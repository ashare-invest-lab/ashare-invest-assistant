# Coverage ratchet (2026-11-12 Grok / Chief ruling)

The CI coverage gate is a ratchet. Overall 80% and domain-package 90% remain improvement goals, not blocking thresholds for O-CI1. The full backend test selection and coverage source remain unchanged. This ruling supersedes the old fixed coverage gate; it does not waive test failures or authorize skipping test groups.

Comparison uses integer fractions, not rounded displayed percentages. A one-line loss fails even if the integer label still passes. Every scope prints the current and base numerators/denominators and denominator delta. `353/436` is **80.9633%**, rounded to 81.0% in the old log: the specifically approved exact measurement is the initial signals floor; the configured 81 is its rounded label, not an extra one-line increase silently imposed on that approved baseline. Explicit later increases (for example 81 to 82) are strict. No ratio decrease from the exact trusted base is allowed.

The policy JSON preserves the reviewed bootstrap unchanged. Its minimum labels may only increase relative to the trusted base. A PR cannot lower a label or rewrite the bootstrap/test-selection manifest to choose its own easier baseline. `check_coverage.py` receives a separately frozen trusted base file, never the PR policy as its measured base.

For the first pre-ratchet main base `465e02046fa8d971897603742497444f884e89a2` only, the loader uses the approved CI counts above. This is an explicit bootstrap because that old run did not upload its raw coverage file. No other missing baseline resets to these counts. The base commit must be present in fetched history.

By the 编排者 ruling at 11-15 19:15 MST, based on `reports/T-O104.md`, only requested base `f6c939d6ed4af94144e7dd669f206c96d6aeaf6b` explicitly recovers from the trusted main push artifact of `90ef8ff16abb7204b7c4ffd54174aeeb8f712455`, after Git verifies that it is the first parent and that every changed path starts with `docs/`.

For later PRs, the base SHA comes from the GitHub event's base repository/main commit. For main pushes it is the actual previous main commit. The loader reads **completed main push** runs of `ci.yml` for that exact base SHA, selects the latest run/attempt and requires its unexpired matching coverage artifact. PR-head artifacts cannot supply the base. The artifact's commit/run/attempt, schema, full-selection manifest and successful ratchet result must all agree. The output of each successful gate becomes the next main commit's measured floor, so improvements cannot subsequently be lost.

裁定①：编排者 11-16 00:40 MST，依据 reports/T-O109.md。PR / merge_group 与 main 事件一样，在精确 main 基线制品缺失、过期、歧义、损坏、身份不符或 `ratchet_passed=false` 等失效情况下，沿 first-parent 回退到最近一个 `ratchet_passed=true` 的 main push 可信制品，最多检查 50 个祖先（`MAX_FALLBACK_ANCESTORS=50`），超限以 `MeasurementUnavailable` 失败。精确头仍有 main push 在运行时，先等待该 run；完成后若制品失效才回退，等待超时仍失败。仍拒绝非 main 来源、PR / workflow_dispatch / foreign 制品和第二父分支，不得重置为 bootstrap。所有制品身份、schema 与完整测试选择等校验保持有效；认证、网络和 Git 错误仍失败。回退成功时 stdout 记录所用提交完整 40 位 SHA 和精确基线失效原因。rc1 时钟由测试冻进 #208，本单不添加 rc1 / portfolio 白名单。

Readiness polls an existing exact-base pending main push every 15 seconds, for the unchanged `--wait-for-main-seconds 1800` budget. Once this invocation has observed a pending run id, it pins subsequent reads to `/actions/runs/<id>` instead of trusting the eventually consistent completed-runs index. The direct result must match the id, base SHA, `main` branch, `push` event, repository and `.github/workflows/ci.yml` path. A still-pending run must finish within the original deadline; pending timeout fails and never authorizes ancestor recovery.

After that known run is first observed completed, only missing artifact data gets a fixed `SETTLE_SECONDS = 120` publication grace, polled every 15 seconds. Empty/missing matching artifacts and HTTP 404 from the artifact list or ZIP download may settle; the grace is never renewed by a later empty response. The order is **wait → settle → classify unavailable → first-parent recovery** for PR, merge_group, main push and main workflow_dispatch. Expired/ambiguous artifacts, invalid measurement identity, `ratchet_passed` other than `true`, or a bad ZIP are unavailable immediately; missing data and artifact 404 become unavailable after grace expires. Recovery prints the selected full SHA, safe reason and skipped-head count. If recovery's list still reports pending after the direct endpoint completed, return to the pinned waiting loop up to the existing 1920-second hard cap, without renewing artifact grace; a direct pending result still uses the original pending deadline. Authentication, rate-limit, server and network errors fail immediately. A run never observed pending gets no grace; its missing artifact or artifact 404 enters recovery immediately. A valid artifact is used as soon as it appears.

The grace may extend beyond the original pending deadline, but `MAX_WAIT_SECONDS = 1920` explicitly caps the polling budget at 32 minutes (1800 + 120 seconds), below the readiness job's unchanged **35-minute timeout**; API requests retain their 30-second timeout. Error annotations include the exception class and a script-owned reason, or only the status code for HTTP errors. Pending timeout reports `timed out after N s waiting for run X`. Library exception messages, tokens, headers and request URLs are not echoed.

Operational evidence supplied for #222: readiness job `133111870788` last logged Waiting at `06:04:57Z`; main `4399512` run `43810192200` completed at `06:05:11Z`, and the next readiness poll at `06:05:12Z` failed after about 20 minutes, before the 1800-second deadline. Its valid `coverage-ratchet-43810192200-1` artifact can now be frozen with the same code. This is a completion/index visibility race, not a wait timeout. Run `43810192200` itself took about **39 minutes** from start to completion: a PR starting alongside a main push may therefore exceed the 1800-second pending budget. Monitor that duration and consider a separately reviewed timing/job-budget adjustment; this change leaves both 1800 seconds and the job timeout intact. #192 is different: both attempts of main `f4e3525` run `43818864753` had `ratchet_passed=false`, an invalid baseline handled by #251 rather than publication grace.

A main-only manual dispatch compares the first parent; dispatching this gate on a topic branch is rejected. The standard workflow needs only read access to contents and Actions; the temporary GitHub token stays inside the baseline-fetch step and is never written into a receipt. Download redirects strip authorization on a host change. No repository write token or auto-commit is used.

For a scope with zero statements, output is N/A, never a claimed 100% measurement. Disappearance of a formerly measured scope fails. When advice/llm first acquire statements, they are measured and must meet at least the trusted overall coverage ratio until their own nonzero measurement becomes the next base; uncovered new packages do not inherit a fake 100% from 0/0.

A missing/empty coverage file, invalid integer counts or disagreement between file totals and coverage totals fails. Changing the declared full test-selection manifest also fails; changed or reduced execution is never absorbed by resetting the baseline. The ratchet does not replace the separate pytest execution/presence checks. Changes to test selection or bootstrap policy require an explicit new ruling, not a PR-local reset.

The coverage artifact `coverage-ratchet-<run>-<attempt>` (90-day retention) is uploaded whenever the ratchet step ran (including a failed comparison), so a flake can still be diagnosed from the original coverage JSON, measurement and backend/selfcheck JUnit. The frozen official measurement still records the raw covered/statement counts; a PR cannot lower those counts or the policy minimums. An unusable exact-base artifact requires a validated recovery under the ruling above; it never gives a default pass.

A separate, temporary file `scripts/ci/coverage-nondet-lines.json` may exclude only named source lines from the comparison (both the current run and the trusted base coverage JSON). Each entry is pinned to the exact statement text at that line number and expires on its `review_by` date (UTC). Anchors are checked against both the HEAD working tree and the trusted base commit's source, read with `git show` (or an explicit `--base-source-root` tree). Line-number drift, a missing statement, an expired entry, or a missing base coverage JSON fails the gate. Exclusions never waive an unregistered line loss. The current entries cover the mutually exclusive session returns in `src/backend/app/aggregates/calendar.py` (T-O104); the lasting fix is to make the tests that exercise `/terminal`, `/today` and `/market/overview` use a frozen clock, or to count the existing fixed-instant selfcheck into the ratchet selection, after which the whitelist should be removed.

The former `--cov-fail-under=80` invocation and fixed 80/90 post-check are replaced by this dedicated ratchet gate. Pytest directories, coverage source, 30-minute job limit and all unrelated test assertions stay in place. Local authors must still report the same full pytest+coverage/vitest commands, actual isolated resource identity, results and gaps before a source push.
